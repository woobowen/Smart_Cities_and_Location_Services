## 1. 两份报告的读者与任务

独立的Experiment Report与Process Report是项目级正式交付规则，适用于本项目正式实验、课程设计及当轮安排的正式报告任务，后续实验同样适用。教师最新明确格式要求仍按既定优先级处理；日常概念问答、临时解释或未授权任务不因此自动生成两份报告。

两份报告都交给课程教师阅读，应当像认真完成实验后的学生报告，而不是纯工程审计、仓库说明书、操作日志或泛化AI长回答。

**Experiment Report**回答：最终做了什么、为什么这样做、结果说明什么。它以真实问题、方法、实验和图表组织技术论证。方法选择、验证机制、比较与取舍属于正文；全部聊天历史不属于正文。

**Process Report**回答：我是怎样与GPT讨论、判断、修改和验证，逐步形成工作流及具体实验决定的。它保留 Workflow Construction 与 Experiment Decision Process 两层，围绕真实判断组织，不是把实验报告写长，也不是接收另一份报告删下来的全部工程内容。

共同事实可在两份报告中承担不同作用：实验报告解释技术理由，过程报告展示理由怎样在真实互动中形成。不能机械复制同一段Brainstorm、同一历史图或同一套叙事。

README用于导航与运行；要求总账用于查漏；日志用于追溯。三者不能替代正式报告。

## 2. Experiment Report 的主叙事

### 2.1 开篇直接说明，主体问题驱动

开篇、目录、必要术语和明确的算法定义可直接说明。正文优先按以下逻辑组织：

**真实问题 / 可说明的风险 → 方法或候选 → 检查与比较 → 实际结果 → 采用、修改、拒绝及局限。**

这是论证关系，不是每个小节都必须设置六个子标题。章节名称可以规范、直接，不要求全部改成问句，也不要求重复“为解决该问题”。

先让读者知道这一步解决什么，再介绍具体实现；先交代为什么需要某个指标，再给公式和读数。能够用一段话自然连接的内容，不拆成大量卡片或口号。

### 2.2 问题驱动不等于编造历史

从结果或典型现象引入一个技术问题是允许的，但要区分“为便于说明，从该现象展开”与“当时正因看见此现象才决定这样做”。只有真实记录支持时才能作历史因果陈述。

不能把后来才发现的失败前置成最初动机，不能声称某篇论文启发了方案而没有当时使用的记录。历史因果主要由 Process Report 与 Evidence Protocol 约束。

### 2.3 以研究问题归组，不以内部阶段拼接

参数的依据、敏感性与最终取舍可归到同一个自然板块；开发、选择、确认仍须准确区分。正文通常不按 Goal 1/2/3、run01、REPAIR-xxx 或内部 Evidence ID 组织。

章节、页数、图表数量和附录长度由老师任务与实际证据决定。已验收报告的25页、七章、10图、17表均不是长期硬指标。不能靠缩字号、删掉负结果或省略必需任务压页数。

## 3. 把研究要求融入实际方法与实验

教师基础与选做任务优先，已批准增强必须与本任务相关。内部建立“要求 → 方法/实验 → 证据 → 正文/图表位置”的映射以防漏项，但不把完整验收大表原样塞进正文。

| 研究要求 | 正文中的自然落点 | 不足以证明完成的替代物 |
|---|---|---|
| 每步有审核 | 关键正确性条件、独立参考、核对方式与代表性结果 | “审核通过”“有Verifier” |
| 优化可量化 | 指标含义、参考、分母、比较方向、保护与代价 | 一个未定义质量总分 |
| 参数有依据 | 教师强制值/示例/default的区别；分布、理论或敏感性依据 | “AI推荐，所以采用” |
| 公平比较 | 共同数据和评价，必要差异与预算明确 | 每个方法各挑最好的一次 |
| 先单项后组合 | 单项、父项、组合与必要移除比较 | 只有参考与完整组合 |
| 结果决定选择 | 哪项实际读数触发采用、保留或退出 | 主观称“最优”“更先进” |
| 允许回退与停止 | 组合退化、无新增证据或有限预算下的具体决定 | 每轮都必须有上升曲线 |
| LLM参与实际任务 | 诊断、真实提议、工具执行、结果反馈及下一动作 | 只展示一段建议 |
| 多Agent有实质职责 | 真实角色判断、状态和工具边界 | 把算法函数重新命名 |
| 记忆有可检验作用 | 来源、检索、消费、动作变化与效果分别检验 | 检索命中率等同收益 |
| AI批判真实 | 对应真实建议或明确假设的反例、前后指标与理由 | 虚构模型错误与用户争论 |
| 可追溯与复现 | 必要设置、来源及可用运行入口 | 主体堆满哈希/日志 |

项目级实质工作流/Multi-Agent要求按Research Protocol §C执行；表中的记忆、特定消融等机制只适用于当轮已授权实验，不因为列出某机制就新增研究任务。方法没有收益可以是有效结论；方法未运行不能写成无收益。

## 4. 正确执行、评价可信与效果支持分开

每一步至少区分三层：

1. **实现是否正确**：输出是否符合算法与数据定义，边界、单位、索引和数值处理是否成立。
2. **比较是否可信**：是否使用共同且独立于候选的参考，样本、分母、上游、预算和聚合是否可比。
3. **效果是否值得采用**：主要指标是否改善，是否违反保护，新增复杂度与收益是否相称，证据支持到什么范围。

整体交付还需检查任务覆盖、正文清楚、图表可读和可复现。测试数、文件数或模型调用数不能直接转化为方法质量；报告获用户认可也不等于全项目已提交或理解已验收。

正式段落可采用“关键条件＋怎样核对＋实测含义”，不罗列全部测试函数。详细反例、逐点账本和运行回执保留工程入口；证明关键结论所需的反例不能仅藏在仓库。

**同一指标必须保持同一参考。**局部算法的保证不自动传递为整条链的保证，候选自身clean上的小误差不能单独证明相对共同原始输入更好。具体数学定义由 Research Protocol 和任务合同确定，本指南不另设得分或退化阈值。

## 5. 参数、组合与迭代的写法

### 5.1 参数不是一串数字

区分初始参考、比较范围、最终采用值和依据。先说明参数会改变什么，再解释用什么实验识别其作用。表格负责完整设置，正文重点解释关键调整及不调整的原因。

没有业务/物理依据的探索网格如实称为离散比较范围，不把它写成已知真值或最优范围。老师明确强制参数不能因润色而成为可调候选。

### 5.2 组合需要可归因的对照

组合比较说明每项改动的独立作用、父方案结果及新增组合是否有额外价值。不能只说“组合优于最初基线”，而不交代它是否优于已有单项。重用已发生且仍有效的单项结果须注明来源，不虚增独立实验。

复杂方案没有获支持时保留简单方案；无收益、退化、权衡与证据不足分别解释。不以论文数、组件数或Agent数代替贡献。

### 5.3 两类循环各自叙述

**研究循环**：候选 → 实际比较 → 支持/拒绝/权衡 → 有依据的下一步或停止。

**工程修复循环**：错误 → 复现 → 修复 → 回归与重建 → 恢复原任务。

正文集中讲清机制，在重要实验处展示它改变了什么决定。不能把修复次数画成质量提升次数，也不能为“持续优化”的故事制造更多失败或永久递增的成绩。

## 6. 中文表达与技术详略

### 6.1 叙述主体

Experiment Report默认由实验问题、方法和观察作主语：“比较发现……”“该设置……”“图中……”。必要时可使用真实的第一人称说明研究选择，但不强制把全文写成个人日记。

AI使用以真实职责简洁披露，不反复写“用户批准”“本工程不代发”。涉及作者自身时不用第三方助手口吻称“用户”。Process Report的“我/我们/GPT/Codex”按Evidence Protocol执行。

### 6.2 不把内部状态当作结果解释

把 `REJECTED / NO_DEMONSTRATED_GAIN / UNVERIFIED` 转为读者能理解的事实说明，而不是简单删除状态背后的限制。例如：

| 不宜作为正文的默认表达 | 可以采用的表达方式 |
|---|---|
| 原始来源坐标系统仍为UNVERIFIED，在用户批准下…… | 数据文件未注明坐标参考系。实验采用固定计算模型作相同条件下的比较，并说明距离含义。 |
| Candidate S3 REJECTED | 该方案增大了共同参考上的几何偏差，因此没有采用。 |
| 全部检查为PASS，所以效果优秀 | 实现检查通过；随后在共同参考上比较覆盖、误差与代价，报告实际改善和限制。 |
| 记忆模块成功运行，因此提升质量 | 检索与引用已经发生；是否改善结果仍需与无记忆方式比较。 |
| GPT＋Codex是用户选择，不能写成老师另行批准 | 在AI使用说明中如实列出两者的职责，正文不讨论未发生的额外授权。 |

以上是表达范式，不是新增实验事实或可直接粘贴为历史对话的原句。

### 6.3 避免空泛，不做机械禁词

避免连续重复“本实验旨在”“通过本实验”“综上所述”和抽象赞美；这些词不是一出现就错误。判断整句是否传递必要信息，而不是用替换词典或禁词扫描假装完成全文改写。

必要术语先用普通语言说明，再定义。保留数学上必须准确的词，不把“覆盖”“压缩”“准确率”“显著”互相替换。表格/图例使用简短名称，正文首次给出完整定义与必要代号。

### 6.4 段落衔接

每个主要比较结束后，指出当前得到什么、下一步仍需回答什么。不要机械重复小结卡片；也不要用“接下来进入Goal 3”作为读者理解实验的桥梁。

结果段落不逐格朗读表格。正文解释关键差异的来源、权衡和例外；表格保存完整数值，图表展示关系。禁止同一结论在数据章、方法章、每个图注和总结中反复作长篇防御。

## 7. 公式、实验设置与复现信息

公式前交代目的，公式后定义变量、单位、参考和边界；复杂推导仅在影响判断时留主体，其余进入简洁附录。

数据划分说明各部分用于什么，不能仅给ID和冻结哈希。开发、选择、最终确认与全量生产身份明确，已暴露数据不能改写成未见测试。

实验设置至少覆盖本任务重要的输入、方法、参数域、运行模式、共同预算、重复次数和统计单位。不同模式必要差异要说明，不以“公平”一词掩盖搜索型模式和一次提议模式的实际预算差异。

模型使用必须真实披露；原始提议、重试、失败与回退按实际记录组织。费用、底层请求不可见时不要虚构精确值，通常无需把所有资源未知项写进主要结果段。

全文关键数值来自已核验结果或明确可复算的描述性汇总。报告重排和重建不是新实验；历史有效结果可以按原实验身份引用，不能冒充当前新LIVE。

## 8. 信息应该放在哪里

| 内容 | 主要位置 |
|---|---|
| 任务目的、数据特征、方法、参数依据、评价定义、比较与主要局限 | Experiment Report正文 |
| 有意义的真实提问、判断、修改、验证与角色/工作流形成 | Process Report正文 |
| 理解方法所需但不适合打断主线的详细公式或参数补充 | 简洁附录 |
| 命令、完整依赖、运行入口、文件结构、包内使用说明 | README/复现说明 |
| SHA256、源码身份、完整回执、逐点账本、失败日志、requirement matrix、Source Audit全表 | 仓库内部追溯材料 |
| 提交邮箱、ZIP命名、是否代发、当前内部验收状态 | 交付清单或任务说明，通常不入报告主体 |

不能把Experiment删下来的全部工程内容转倒进Process或附录。影响结论的坐标未知、采样偏差、无真值、不可计算分母和不利案例仍须在适当正文位置解释。

若老师明确要求某种运行截图、复现步骤或状态说明，按要求提供；本表不是绕过教师任务的理由。

## 9. AI、Workflow与Multi-Agent的表达

先解释真实任务中的困难，再解释角色分工如何帮助完成处理、检查或下一轮比较。必须区分：

- **研究/生产治理层**：谁规划、执行、核验和修复整个任务。
- **被评估方法层**：某个模式在一次记录级/请求级决策中看见什么、调用什么、怎样选候选。
- **最终部署层**：实际冻结的处理流程是否还使用逐条模型、搜索或记忆。

不能把治理层使用LLM当作search-only内部模型调用；也不能因为最终固定策略无模型，就声称此前LLM/记忆实验没有做。体系的实际职责、方法效果及因果贡献分别表述。

Agent负责的判断和工具边界应明确；普通算法函数不因命名带Agent就获得独立判断职责。保留必要反馈、拒绝、回退和停止关系，图中没有真实实现的能力只能标为未采用候选，不能画进最终系统。

技术核验图说明共同输入、候选、可信参考、检查和结果判断，不强行补“用户发现问题”节点。只有原始互动确有对应动作，才能用Process的Human Reasoning图语法讲这段历史。

AI批判说明实际建议/假设、核验方式和证据。模型提出“待检验候选”不等于它曾宣称该方案最优；不能为强化批判改变原话的确定程度。

## 10. 图表与文字共同承担证据

图型、精确P2编码、三维/流向/分布/框架图的技术条件由Visual System §§11—13规定。本节负责它们在文章中的用法。

每张主要图先明确：要回答什么问题、使用什么真实输入、与哪组结果相连、读者应看什么、正文补充什么。图表不是给已有段落加装饰，也不能拿几张复杂主图替代其他必做实验。

图题命名比较对象或技术问题。图注提供必要的样本、设置、单位、编码及一项主要发现；不能将图注写成运行日志，也不能只重复图题。不同参考的误差、不同分母和未测试格子必须在图内/图注说清。

正文引用图表后解释机制或取舍，不把所有数字再读一遍。重要的负结果、局部边界或样本差异应可见，不只选择“最好看”的案例。案例选取依据保存于内部记录。

正式PDF应在静态阅读下成立；交互HTML可以补充，不能要求教师旋转/点击后才看见关键证据。最终字体、图例、轴范围、留白和图注需按实际页面检查。

## 11. 22类全文编辑检查

以下将已确认的写法归纳为长期检查类型，不要求未来任务再逐项进行A/B/C选择，也不锁定实验一的实际图型。

| ID | 类型 | 默认处理 |
|---|---|---|
| W01 | 章节与顺序 | 开篇与目录规范直接；正文按问题和比较关系组织，不按内部Goal拼接 |
| W02 | 开篇任务 | 简洁交代任务和阅读路径，不以提交管理和长范围声明起篇 |
| W03 | 主体与AI职责 | 集中、真实披露工具角色；正文用实验事实而非“用户批准”口吻 |
| W04 | 工程信息 | 长哈希、状态、权限与提交清单退出主体；保留简短复现入口 |
| W05 | 假设与未知 | 用自然语言或数据表解释事实缺口和影响，不删除限制 |
| W06 | 代号与术语 | 中文改动名称优先，必要代号首次定义，图例保持简短一致 |
| W07 | 算法与公式 | 先说明问题与用途，再图解/定义；细节按科学必要性分层 |
| W08 | 参数依据 | 区分参考、比较范围、最终值和选择理由，避免数字堆砌 |
| W09 | 逐步核验 | 实现检查与效果比较分开，在对应方法中说明关键条件 |
| W10 | 量化优化 | 先解释评价漏洞，再给共同参考、分母、方向和含义 |
| W11 | 公平与确认 | 说明样本用途和必要模式差异，最后确认不作反复调参入口 |
| W12 | 单项与组合 | 父项对照和新增贡献可见，不只比较最复杂方案与最弱基线 |
| W13 | 迭代与停止 | 研究取舍与工程修复分开，不伪造每轮增益或无限循环 |
| W14 | Agent角色 | 区分治理、被测模式与最终运行，普通函数不改名充数 |
| W15 | LLM实际行动 | 权限、提议、工具执行与真实反馈可见，预算口径明确 |
| W16 | 正负结果 | 运行完成与采用依据分列；无收益、退化、权衡、未证明不混称 |
| W17 | AI批判 | 真实提议—执行—判断，保留原确定程度，不虚构人类挑战 |
| W18 | 结果段落 | 解释差异来源、代价与例外，不逐格朗读表格 |
| W19 | 图题图注 | 对象/样本/条件/编码清楚，结论不超出图示证据 |
| W20 | 文献作用 | 实際用到处给出处，思想、实现与事后对应分开 |
| W21 | 段落衔接 | 用已有结论和仍未解决的问题引出后续比较 |
| W22 | 总结与不足 | 总结技术认识与最终取舍，集中保留局限，不宣布工程状态当结论 |

## 12. Process Report写作衔接：不覆盖最新第一人称规则

后续任务继承已经真实形成的项目工作流作为共同基础，根据报告独立可读性作必要介绍或引用，重点记录本次新增、修正、否定及本次Experiment Decision Process。不从零重写相同历史，不机械复制31页前期材料，也不制造争论来表现迭代。继承须保留来源、实际适用范围和原有Lock状态，不能将局部参考扩大为整份报告已完成；Evidence Master的指定与职责见Evidence Protocol §4.1。

Process正文按Evidence Protocol §16.1—16.2执行：自己的观察、质疑、判断与选择写“我”，真正共同完成的动作才写“我们”，GPT/Codex按真实职责直接称呼。主体为自然研究叙事，关键判断保留人的自然语气，技术定义保持简洁准确。

报告可整理真实事实形成连贯文字，但不能改变提出者、时序、确定程度和证据出现顺序。后来由GPT形式化的术语，不倒写成用户最初已经熟悉。内部Block和Evidence ID不机械成为正式章节。

“改报告文风”的授权只作用于报告叙述，不授权把截图中的用户原话专业化、生成新聊天、伪造回合或重画UI。引用、裁切与重构仍按最低干预等级、原文审查及Evidence Master规格执行。

前期Workflow Construction参考只用于相应范围，不能证明后期Experiment Decision Process已经形成，也不能代替具体Evidence Lock。一般路径修复与编译日志仍留内部；真实改变研究工作流的事件才有进入正式叙事的理由。

## 13. 制作、接管与改稿顺序

可用真实输入和工具齐备、任务已授权时，优先由GPT直接完成文字、原生图表与排版，让用户检查实际样页/成品；缺少输入时先按现有工具查找，不凭摘要重建实验图。

整篇重大重构通常先确定内容—论证—图表蓝图，再用代表性样章和真实例图检验风格，确认后完成全文。用户已明确批准方向并要求全篇完成时，直接继续，不把同一选择再问一遍。

这是工作效率规则，不要求每个小修都制作三套样稿。普通排版、错别字和已批准改动内的修复直接完成；改变技术含义、证据关系或主要视觉选择时才重新讨论。

作者交付正文/图表的可编辑源、真实输入或可取回的数据标识、构建入口与已做检查。Codex负责接入仓库、修正生成器、运行影响范围回归与发布，不从旧模板重新生成一篇“意思相近”的报告覆盖用户已验收版本。

GPT自己制作后的检查是作者自检，不标为独立审核。独立检查说明实际执行者、对象、方法和范围；用户验收文稿、工程集成、Evidence Lock及最终提交状态分别记录。

## 14. 正式文稿审核

### 内容与论证

检查教师任务与获批增强的覆盖；重要方法是否有动机、明确操作和核验；比较是否能回答问题；结论是否与具体图表/数据相连；负结果和限制是否保留。

不能以删去工程口吻为由删去必要方法、共同参考、无真值、坐标未知或AI使用说明。反过来，也不能因内部记录存在就认为正文不必讲清关键问题。

### 表达与视觉

全文检查真实叙述主体、术语、重复、段落衔接、标题和图注。实际PDF逐页渲染并查看，不只看文字提取、缩略图、文件存在或编译成功。具体渲染/PPI与证据检查按Visual System、AGENTS和Evidence Protocol。

### 复现与变更

检查PDF、源文件、图表输入、数字来源、页码导航和提交包是否对应当前有效内容。纯文档变化不自动重跑全部实验；实现或评价变化必须检查受影响结果，不通过保留旧回执掩盖变更。

源码可编译不自动证明图表可以从输入重建；两项分别记录。精确未做过的检查写明，不将作者自检或旧版本检查冒称新的独立执行。

## 15. 已验收参考成品与长期复用

已批准的Experiment PDF及对应源包是具体写作、图表和排版参考；参考清单和角色由Visual System §16统一登记，实际文件来源与哈希由内部Source Manifest维护。

阅读成品以理解内容和视觉；读取源文件以复用构建方式。PDF和ZIP必须对应同一版本，改动任一方后重新检查配对。包内数据仍属于原任务，不成为新实验的输入或结果。

通用模板保留稳定P2与排版组件，合成示例保持合成身份；不得将已验收任务报告覆盖成合成模板，也不得把真实数据和结论直接塞进通用模板。已验收成品对具体文风和页面效果提供参考，但不能静默推翻研究真实性和Evidence规则。

长期固定的是报告定位、自然问题驱动的论证、第一人称Process真实性、共同视觉身份与可核验表达；不固定页数、章数、图表数量、三维图配额、论文采用数或特定实验方案。

## 16. 更新原则

本指南是详细写作入口。新增长期写作规则优先更新这里，并在Visual System、Evidence Protocol、AGENTS及Project Settings中只同步职责或必要短引用。P2色值与Evidence生产规则仍由原负责文档维护。

发生歧义时回到当前明确用户要求和对应材料，不以旧报告的某一句话作为比新确认更高的规则。所有真实原件、已有有效成果及确认记录保留历史；只有一个明确的当前有效规则版本。
