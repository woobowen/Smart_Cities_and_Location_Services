## 3. 必修问题与明确的验收方向

### R1-F01：完整 profile 审核前不得丢掉错误行

当前 tools.py 在 verify_profiles/recompute_check 中先用 dict 去重并过滤 ID，再让独立审核器检查，掩盖原始列表的重复和越界记录。

实际反例：应有1条记录，却提交两行同ID或一行额外 foreign ID。直接 independent_profile_review 会拒绝，经过工具接口却 VERIFIED，recompute_check 甚至 exact_match=true。

修复要求：
1. 在任何去重、重排、过滤之前，检查输入是结构正确的列表，记录 ID 唯一，数量和集合与声明作用域完全相符。
2. 通过集合验证后才能按 canonical ID 顺序对齐，合法列表重排仍应通过。
3. 缺失、多余、重复、字段错误都产生明确失败，不能用“清理审核输入”修复成通过。
4. 若将来支持子集，必须显式声明子集，不改变本轮全部七条 pilot 的范围。
5. 为 verify_profiles 和 recompute_check 各增加重复/额外/缺失/顺序变化及正常输入测试。

### R1-F02：数据与模型事件异常必须形成清楚的结束状态

已复现：
- duplicate_details('fixture', [[None,1], [[0,0],[0,0]]]) 抛 TypeError。
- visible_events 读取 {"type":"item.started","item":null} 抛 AttributeError。
- provider 子进程启动 OSError 逃逸，call目录只有input.json，没有终止receipt。
- timeout虽然保存receipt，但丢掉已产生的可见事件和stderr。

修复要求：
1. 明确结构有效、数值有效和某个量可计算的区别；缺失时间不直接相减。可继续的诊断保留结果和不可用原因，不能补0速度或改原始数据。
2. 先校验事件/item结构，再访问字段。无效输出是协议失败，不做正则补JSON、丢错误装成功。
3. 对可预期的数据、I/O、启动、解析、数值工具异常，生成绑定call_id/run_id的失败记录，更新checkpoint及manifest，避免永久停在RUNNING或DISPATCHED。
4. 不能捕获后返回成功。中断、写盘失败或结果未知时准确说明，不自动重发可能已经执行的模型任务。
5. 安全保留已产生的可见事件、退出码、已知错误及解析失败位置；不保存隐藏推理、认证内容或无关账户日志。无法保存时明确报告证据缺失，不宣称完整记录。
6. 保留现有进程组终止措施，测试父子进程确实停止产生后续副作用。不要为了恢复调用关闭沙盒或TLS。
7. 增加实际异常路径测试，而不只测试inject_failure这个特殊分支。

### R1-F03：把研究门控与未实现入口分开

当前 denoise_trajectory 永远抛 MethodUnresolved；baseline 永远返回BLOCKED；controller的阶段动作列表没有完整处理入口，最后状态也固定写BLOCKED。因此不是把配置改成APPROVED就能执行。

修复要求：
1. 保留 unresolved preflight，但将方法注册/合同核对与实际 runner 分开。
2. 接通“分段→独立短片段过滤→获批去噪→DP→独立评价→点去向账本”的调用关系；复用已正确工具，不大规模重写。
3. 实际生产 runner 只能接受有真实依据且明确获批的语义与方法合同。合同未完备时准确返回具体阻断项；不能以测试构造的approval对象解锁真实数据。
4. 控制器允许当前条件下合法的诊断或处理动作；不能始终强制每个角色只输出一个写死动作而声称完成了处理决策。
5. 工程验证使用明确构造的平面输入；真实 baseline 必须仍从教师原始数据出发，在前提获批后产生真实结果。
6. 不把桩函数、测试替身、dry-run或仅前置检查称为完整处理链。尚未获批部分标清暂缺，而不是伪实现一个默认方法。
